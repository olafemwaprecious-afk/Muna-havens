# Security model

Who is allowed to do what, and where that is enforced. Read this before changing
`db/migrations/0002` or `0003`, and before adding any table.

The one sentence: **the browser is never trusted, and nothing in this repository
grants access.** Every permission is a policy in PostgreSQL. If a rule only
exists in JavaScript, it is a usability feature, not a security feature.

---

## Who the actors are

| Role | What they may do |
| --- | --- |
| `anon` (any visitor, signed out) | Read the four `mh_public_*` views. Nothing else: no base-table read, no write, no order, no settings row. |
| `authenticated`, not an owner | Sign in, read their own `mh_app_role` row (which will not be there), and be refused by every other policy. They cannot read raw products, orders, settings or storage. |
| `authenticated`, an owner | Everything the dashboard can do: products, categories, variants, stock, images, orders, settings. |
| `service_role` / `postgres` | Outside the app's trust model. The browser must never hold such a key. |

There is no other role. The schema has exactly one: `mh_app_role.role`, checked
against `check (role in ('owner'))`.

## What decides ownership

```sql
create or replace function public.mh_is_owner()
returns boolean
language sql
stable
security definer
set search_path = public, pg_temp
as $$
  select exists (
    select 1
    from public.mh_app_role r
    where r.user_id = (select auth.uid())
      and r.role = 'owner'
  )
$$;
```

That is the whole function, copied from `db/migrations/0001_muna_haven_schema.sql`
— `tests/schema.test.mjs` fails if the two drift apart, because a security document
that describes a *different* check than the one deployed is worse than no document.

Three things in that definition are load-bearing:

* **`security definer`** — the policy needs to read `mh_app_role`, but a signed-in
  non-owner must not be able to read that table directly. Definer rights give the
  check without giving the table.
* **`set search_path = public, pg_temp`** — without it, a schema-search trick could
  substitute a different `mh_app_role`. Pinning it closes that.
* **membership, not authentication** — "can sign in" is not "owns the store". The
  join to `mh_app_role` is the whole difference, and it is why granting ownership
  happens in the SQL editor and never in the site.

Every owner policy is `to authenticated` with `using (public.mh_is_owner())` (plus
`with check` on writes). The read-only policies on `mh_app_role` are the exception:
`mh_read_own_role` lets a user see their own row and nothing else.

## The grant surface, and why it is shaped like this

* `anon` gets `select` on the four public views. Nothing else. The base tables are
  explicitly `revoke all … from anon` — one statement per `mh_` table, never a
  schema-wide revoke, because this project may share its database with other apps
  and a blanket statement would break them.
* `authenticated` gets table-level `select/insert/update/delete` on the owner
  tables, which does *not* mean access: row-level security then decides every row,
  and `mh_is_owner()` decides everything. Table grants without a matching policy
  grant nothing.
* The public views are **owner-privileged** (no `security_invoker`). They carry an
  explicit `where status = 'published'` and a column whitelist, which is the
  actual published-only guarantee. `0005` proves both halves: a shopper can read
  the view, and is refused on the base table.
* **`force row level security` is deliberately not used.** It would apply the
  policies — which name only `anon` and `authenticated` — to the owner path the
  views rely on, and the storefront would render empty. That reason is written
  into `0002` and asserted in `tests/schema.test.mjs`, because the absence of a
  line is the kind of thing a careful reviewer later "helpfully" adds.
* No migration creates a user, sets a password, or grants anything `to public`.

## Secrets

* `assets/js/config.js` — generated by `scripts/build.mjs` from `.env`, and
  gitignored. It holds only the project URL and the publishable key, both of which
  are, by design, in every visitor's browser.
* `scripts/build.mjs` refuses to write the file if any of its inputs looks like a
  secret key, a JWT, a private key block or a database URL. A wrong paste fails
  the build instead of publishing a credential.
* `scripts/check.mjs` scans the whole tree for those same patterns on every run
  (`npm run check`), and the Pages workflow greps the *built output* before upload.
* The owner account is created in the Supabase dashboard and no password or email
  for it appears in this repository.
* `.env.example` lists the two public values and names what must never appear.

If a secret key is ever committed: rotate it in Supabase immediately. Deleting the
file does not remove it from history, and rotation is the only reliable fix.

## What the client can and cannot do

| Attempt | Result |
| --- | --- |
| `GET /rest/v1/mh_products` as anon | refused — no grant, no policy |
| `POST /rest/v1/mh_products` as anon | refused before the row is written |
| `PATCH` a price as anon | refused |
| `INSERT` into `mh_app_role` as a signed-in non-owner | refused (`0005` asserts it) |
| Reading a draft or archived product through the view | not returned — the view filters |
| Asking a view for `stock_quantity` or `image_licence_note` | error: the column is not in the view |
| `DELETE` of a storage object still used by another product | refused by `mh_delete_unreferenced_image()` |
| A crafted request that skips the dashboard entirely | identical outcome: policies run on the request, not the UI |

Order lines snapshot the product name and unit price so a later edit cannot
rewrite what a customer was quoted; the total is derived from the lines by a
trigger rather than accepted from the client. `mh_guard_publish` enforces
completeness in the database, so an API call cannot publish an empty listing even
if the form is bypassed.

## XSS and rendering

Every string from the database goes through `textContent`
(`assets/js/lib/dom.js`). There is no `innerHTML` path for data anywhere in the
app; the only markup assigned directly is a fixed set of developer-authored SVG
icon strings. A product named `<img onerror=…>` is shown to the customer as those
literal characters — `tests/render.test.mjs` asserts exactly that, including that
no `script`, `b` or injected `img` element is created.

Storage keys are chosen so nothing sensitive persists: the session under
`muna-haven-auth` and no cart, no customer data, no notes. A stolen session token
still passes through the same owner check on every query, which is the point of
doing the authorisation in Postgres rather than in the page.

## What this does **not** protect

Being honest about the boundary, because a security document that overstates
itself is worse than none:

* **The public catalogue is public.** Anyone can read every published product,
  price and description, and can enumerate them through the view. That is a shop
  window, and the `mh_public_*` views are the whole exposure.
* **The publishable key is not a secret**; it is an identifier. It does not rate
  limit, and rate limiting, WAF and brute-force protection on the auth endpoint
  are Supabase platform settings, outside this repository.
* **Image URLs in the public bucket are unguessable, not access-controlled.** The
  bucket read policy allows public read of `muna-haven-product-images` by design.
  Anything that must not be public does not go in that bucket — customer phone
  numbers, ID documents, payment screenshots.
* **A customer's WhatsApp number is personal data**, stored in `mh_orders` and
  readable only by an owner. There is no encryption at rest, no retention policy
  and no delete-my-data flow in version 1. If that matters for your jurisdiction,
  that is a real gap to close, not a detail.
* **Physical and account security is yours**: a weak owner password, a leaked
  Supabase dashboard session or a compromised GitHub account with repo admin
  rights defeats everything above. Enable MFA on both.
* **The migrations must actually run.** Until `0002` has been applied to your
  project, tables can exist with no policies at all — which is the one state in
  this document that is genuinely dangerous, and precisely what
  `tools/access-check.html` measures.

## Verifying it, not assuming it

```
npm run check                     # brand rules, secret scan, migration safety
node scripts/build.mjs && npm start
# then, on the deployed site:
<site>/tools/access-check.html → press “Run the checks”
```

and in Supabase:

```
db/migrations/0005_muna_haven_verification.sql   # runs in a transaction, rolls back
```
and on the deployed site, `https://<owner>.github.io/Muna-havens/tools/access-check.html`.

The results of the last two cannot be produced from this repository — they need
your project and your browser. Treat "secured by RLS" as *claimed* until those
report `PASS`.
